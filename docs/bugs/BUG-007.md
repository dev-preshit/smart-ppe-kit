# BUG-007 Motor output stays ON for about 540 ms when the task watchdog fires during an ON pulse (M-08 not met)

| Field | Value |
|---|---|
| Severity | P1 (motor safety, NFR-05) |
| Status | Fixed in f971297, regression PASS (rehearsal); closes with the evidence sitting |
| Reported by / date | S5 engineer (Claude Code session), 2026-11-23 |
| Found in | TC-30b rehearsal (scratch, not evidence), sprint S5, firmware 1c18cc6 (FW hub=2e914c45 common=f27ca4fc); the code is from f5f520b |
| Requirement(s) | NFR-05 (never on continuously, off in every fault, longest ON <= 400 ms), FR-30 |
| State machine transition(s) | M-08 (task watchdog or scan reboot: output low before the restart), X-02, M-05 |
| Finding link (if related) | none |

## Environment
- Firmware: hub bench build (PPE_TEST_HOOKS) at 1c18cc6, built and flashed with tools/s5_build.py. Recorder: tools/edge_recorder on COM8, calibrated the same sitting (worst error 13 us).
- Toolchain: arduino-cli 1.5.2-rc.1, esp32 core 3.3.12 (ESP-IDF 5.5), CONFIG_ESP_TASK_WDT_PANIC=1, CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=1.
- Motor pin: hub GPIO 5 into the bench driver (A-40); recorder channel 0 on the node before the base resistor.

## Steps to reproduce
1. `python tools/s5_motor.py tc30b --tc TC-30b --hub COM3 --rec COM8 --rehearsal` (alert pattern 300/700 ms running, then hook `fault wdt`).
2. The watchdog fires about 5 s after the hook. If that moment falls inside a 300 ms ON pulse, the output stays high until the chip resets.

Reproducibility: the watchdog fires at a phase locked to the hub's 1 s pattern (at f971297 always 150 to 190 ms into an ON pulse, in 15 of 15 resets), so on a given build it reproduces almost always or almost never. Seen at 1c18cc6; the f5f520b run on 2026-11-21 passed (the WDT fell in an OFF period on that build).

## Expected (SRS acceptance criterion)
NFR-05: maximum continuous ON <= 400 ms over faults including a WDT reset; M-08: output low before the restart.

## Actual
`test_logs/scratch/TC-30b_1c18cc6.log` (git-ignored scratch log): rising edge at recorder t=265199000 us (line 82), the task_wdt panic prints its report (lines 83-106), the pin falls at t=265737244 us (line 117) when the chip resets, before 'HUB boot'. ON = 538.2 ms. Analyzer verdict FAIL ('an ON run is longer than 400 ms').

## Analysis
- Root cause: B-05 configures the task watchdog with trigger_panic = true (f5f520b). The panic handler prints the backtrace at 115200 baud and then restarts; nothing drives the motor pin low first. The 395 ms guard (esp_timer) and the motor task cannot run while the panic handler holds the CPUs. M-08 'output low before the restart' was not implemented.
- Why earlier tests did not catch it: the host tests model the pattern FSM, not the panic path; the only bench run before (f5f520b) hit an OFF period.
- Affected: TC-30 (WDT fault), TC-74 (1 h with injected WDT), NFR-05. Not affected by the 1c18cc6 identity change (the FW line prints after the reset).

## Fix (applied in f971297, approved by Preshit 2026-11-23)
- `esp_task_wdt_isr_user_handler()` (weak hook in ESP-IDF 5.5, called from the task watchdog ISR before the abort) in IRAM drives GPIO 5 low by a direct register write and sets a flag that keeps drive() low until the restart. The esp_restart paths (scan-stall reboot X-01, fault hooks) already call hub_motor_safe_off() before ESP.restart(), so no shutdown handler was added.
- Residual: any other panic (a crash in code) is not covered by this hook; the pin then stays at its last level until the reset (a few hundred ms). Listed as residual risk (owner chose the watchdog-only fix, 2026-11-23).
- Approved requirement change needed? No (the fix implements M-08 as written).

## Regression
- `python tools/s5_motor.py wdton --hub COM3 --rec COM8 --rehearsal` (15 x fault wdt while the alert runs). PASS needs every ON <= 400 ms and >= 5 ON pulses cut by the WDT. Host analyzer tests in tools/tests/test_s5_motor.py (Wdton); the 1c18cc6 failing log still reads FAIL 538.2 ms through it.
- Fails before the fix: yes (1c18cc6 log). Passes after the fix: yes.

## Retest
- f971297 (FW hub=bbade3e7 common=f27ca4fc), test_logs/scratch/BUG-007_f971297.log (rehearsal, not evidence): PASS, 15 ON pulses cut by the watchdog at 149.4..191.4 ms, longest ON of the run 301.0 ms; the pin falls with the first task_wdt line and stays low through the panic print and the reboot.
- Not verified: a watchdog at other phases of the ON pulse (the WDT phase is locked on this build). By the mechanism the ON is at most 300 ms plus the ISR latency at any phase.
- Residual risk: other panics (a crash in code) are not covered by this hook.
